# Deck Blueprint Section

This stage turns validated research and issue analysis into a banker-quality page blueprint.

The LLM owns:
- deck storyline;
- each slide's investor question and page thesis;
- selected issue analysis blocks;
- template variant choice within `template_registry.json`;
- conclusion-led headline, main message, body blocks, visual intent/data, caveats, and open questions.

Scripts own:
- template registry extraction;
- evidence-contract derivation;
- renderer-spec compilation;
- formal validation.

Do not hand-write `page_evidence_contract.json` or `renderer_spec.json` in formal runs. If page content needs changing, edit `deck_blueprint.json`, revalidate it, and recompile.

## Required Inputs

- `industry_research_pack.md`
- `industry_issue_analysis.json`
- `artifacts/issue_analysis_validation.json`
- `template_registry.json` generated by `scripts/extract_template_registry.py`

## Step 1: Extract Template Registry

```bash
"$PYTHON_CMD" scripts/extract_template_registry.py \
  --output template_registry.json

"$PYTHON_CMD" scripts/validate_template_registry.py \
  --template-registry template_registry.json \
  --slide-registry templates/slide_registry.json \
  --output artifacts/template_registry_validation.json
```

Use `template_registry.json` to understand which page types, body fields, charts, tables, cards, and capacity constraints are available. Do not infer unsupported layouts.

## Step 2: Write `deck_blueprint.json`

Write one JSON file:

```json
{
  "schema_version": "deck_blueprint_v1",
  "section_meta": {},
  "deck_storyline": "...",
  "slides": []
}
```

Each slide must contain:
- `slide_no`: 1-8;
- `fixed_page_role`: the fixed role for that slide;
- `investor_question`: the investor question this page answers;
- `page_thesis`: the page answer in banker reasoning language;
- `issue_analysis_ids`: the IA blocks used by this page;
- `selected_page_type`: a formal-allowed page type from `template_registry.json`;
- `claim_strength`;
- `headline`: client-facing, conclusion-led PPT title;
- `main_message`: one sentence explaining the page logic;
- `body_blocks`: distinct PPT-ready content blocks;
- optional `visual_design`, `chart_data`, `compare_table_data`, `visible_metric_claims`, `strategy_checks`, `caveats`, `open_questions`.
- optional editorial helper fields such as `page_rationale`, `visual_rationale`, or `editor_notes`; compilers ignore these, but they can help preserve page logic.

Body blocks are not research notes. They should read like PPT copy:

```json
{
  "role": "market_size",
  "target_field": "bullet_1",
  "copy": "该行业已具备可观市场体量，足以支撑买方对平台型资产的并购讨论",
  "source_analysis_ids": ["IA-001"],
  "evidence_ids": ["EV-001"],
  "metric_ids": ["MET-001"],
  "claim_strength": "hard_fact"
}
```

Good body block = label or role + data/mechanism + why it matters.

Bad body block = raw fact pasted from research pack with no implication.

Do not add weak body blocks just to fill every active template field, but do not leave a page thin merely to avoid body-copy length warnings. Body copy should be **dense but scannable**: preserve the proof layer, mechanism, comparison, and implication needed for the page thesis. If a page feels empty, first add real evidence-backed content, use a richer visual/table, or return to research; only choose a simpler page type when the argument itself is genuinely narrow.

Title and subtitle fields have hard fit constraints. Body fields do not hard-fail only because they are long; length warnings are editorial scanability prompts, not permission to delete evidence or logic.

Use `target_field` when placement matters. For example, a value-chain page can map `upstream` to `top_left`, `manufacturing` to `top_center`, `brand` to `top_right`, `channel` to `bottom_left`, `profit_pool` to `bottom_center`, and `transaction_implication` to `bottom_right`. If `target_field` is omitted, the compiler will try role-based mapping first and sequence-based fallback last.

For visible numeric claims, bind the number at the exact field/location where it appears. Use `metric_ids` as an array; do not maintain a separate single `metric_id` field in the blueprint:

```json
{
  "location": "body_copy.bullet_2",
  "display_text": "2024年市场规模约937亿元，已具备平台型并购讨论基础",
  "metric_ids": ["MET-001"],
  "evidence_ids": ["EV-001"],
  "usage_type": "direct_display",
  "basis_note": "All-channel retail sales, China, 2024"
}
```

`scripts/repair_visible_metric_claims.py` repairs compiled `renderer_spec.json` only. If content-quality validation points to a blueprint problem, edit `deck_blueprint.json` and recompile instead of running the repair script directly on the blueprint.

## Fixed Slide Roles

- Slide 1: `industry_overview`
- Slide 2: `market_size_segmentation`
- Slide 3: `key_industry_drivers`
- Slide 4: `value_chain_profit_pool`
- Slide 5: `key_barriers_value_drivers`
- Slide 6: `competitive_landscape`
- Slide 7: `industry_trends_future_evolution`
- Slide 8: `transaction_implications`

Do not force target promotion. Target context should be selective, evidence-based, and clearly separated from industry conclusions.

## Blueprint Quality Rules

- One slide answers one investor question.
- Headline must be a point of view, not a source table label.
- Main message must not repeat the headline.
- Body blocks must be distinct; do not fill multiple fields with the same metric.
- Body block count does not need to equal template field count. Use as many blocks as the page argument genuinely needs.
- When a block has a deliberate placement, set `target_field`; do not rely on array order for semantically different template regions.
- For `compare_table_page`, put table headers/rows only in `compare_table_data`.
  Do not duplicate `table_header` or `table_row_*` as `body_blocks`; those fields
  are rendered as the native table and the active body fields are the surrounding
  analysis panels.
- A chart must serve the headline. Do not add charts just because the template can display one.
- Every material number in headline, main message, body block, chart, table, or metric card must bind to allowed MET IDs.
- Every body claim must bind to EV IDs from selected issue analyses.
- Do not use an IA block downstream if its `downstream_permission` disallows the intended use.
- If evidence is thin, make the page a caveated implication or open question instead of a confident conclusion.

## Step 3: Validate Blueprint

```bash
"$PYTHON_CMD" scripts/validate_deck_blueprint.py \
  --deck-blueprint deck_blueprint.json \
  --issue-analysis industry_issue_analysis.json \
  --template-registry template_registry.json \
  --output artifacts/deck_blueprint_validation.json
```

If this fails, repair `deck_blueprint.json` or go back to `industry_issue_analysis.json` / research when the evidence is genuinely insufficient. Do not patch downstream compiled files.

If it passes with warnings, read `artifacts/deck_blueprint_validation.json`.
Warnings such as "headline may be a label rather than a conclusion-led title"
are not formatting noise: they usually explain why a valid deck feels thin or
mechanical. Use `warning_repair_plan.targets[]` to repair the named
`deck_blueprint.json` fields before compiling unless the warning is plainly
irrelevant for the selected page.

## Step 4: Compile Derived Artifacts

```bash
"$PYTHON_CMD" scripts/compile_deck_blueprint.py \
  --issue-analysis industry_issue_analysis.json \
  --deck-blueprint deck_blueprint.json \
  --template-registry template_registry.json \
  --page-contract-output page_evidence_contract.json \
  --renderer-spec-output renderer_spec.json
```

This compiler creates:
- `page_evidence_contract.json`;
- `renderer_spec.json`.

## Diagnostic: Banker Review Packet

When page quality is hard to diagnose, build a compact review packet and read it
like a banker reviewer. This is not a gate, not part of the main workflow path,
and not another artifact to fill by default. It helps the LLM focus on page
quality instead of schema repair.

```bash
"$PYTHON_CMD" scripts/build_banker_review_packet.py \
  --deck-blueprint deck_blueprint.json \
  --page-contract page_evidence_contract.json \
  --renderer-spec renderer_spec.json \
  --output artifacts/banker_review_packet.md

"$PYTHON_CMD" scripts/build_banker_review_report_skeleton.py \
  --deck-blueprint deck_blueprint.json \
  --page-contract page_evidence_contract.json \
  --renderer-spec renderer_spec.json \
  --output artifacts/banker_review_report.json
```

Review:
- Does each page answer one investor question?
- Is the headline a point of view rather than a metric label?
- Does body copy have enough evidence, mechanism, comparison, or implication?
- Does the visual support the headline?
- Are thin/proxy/user-provided facts caveated?
- Are adjacent pages non-duplicative?

If review finds issues, repair `deck_blueprint.json`, then revalidate and
recompile. Do not patch `renderer_spec.json` or PPT output directly.

`banker_review_report.json` is a structured workspace for the LLM reviewer. It
is not a gate, but it makes repair targets explicit: page quality, evidence
support, copy density, visual support, and the upstream file to edit. Fill the
judgment fields if useful, then repair `deck_blueprint.json` or upstream
research artifacts.

## Step 5: Validate Compiled Artifacts

```bash
"$PYTHON_CMD" scripts/validate_page_evidence_contract.py \
  --issue-analysis industry_issue_analysis.json \
  --deck-blueprint deck_blueprint.json \
  --page-contract page_evidence_contract.json \
  --output artifacts/page_evidence_contract_validation.json

"$PYTHON_CMD" scripts/validate_renderer_spec.py \
  --renderer-spec renderer_spec.json \
  --template-registry template_registry.json \
  --deck-blueprint deck_blueprint.json \
  --page-contract page_evidence_contract.json \
  --output artifacts/renderer_spec_validation.json

"$PYTHON_CMD" scripts/validate_chart_metric_binding.py \
  --renderer-spec renderer_spec.json \
  --research-pack industry_research_pack.md \
  --page-contract page_evidence_contract.json \
  --output artifacts/chart_metric_binding_validation.json

"$PYTHON_CMD" scripts/validate_content_quality.py \
  --renderer-spec renderer_spec.json \
  --research-pack industry_research_pack.md \
  --rules templates/content_quality_rules.json \
  --text-fit-rules templates/text_fit_rules.json \
  --layout-budget templates/layout_budget.json \
  --output artifacts/content_quality_validation.json
```

If compiled validation fails, read the validation JSON before editing. For
`artifacts/content_quality_validation.json`, use:

- `root_causes[]`: grouped issue categories;
- `repair_plan.primary_repair_targets`: the first artifacts to edit;
- `repair_plan.targets[].repair_fields`: the specific upstream fields to repair;
- `repair_plan.rerun_steps`: the required validator / compiler sequence.

Default repair target is `deck_blueprint.json`. Return to
`industry_research_pack.md` or `industry_issue_analysis.json` only when the
repair plan names them as fallback targets because the evidence / metric is
missing or too thin. Do not patch `renderer_spec.json`, `replacement_dict.json`,
or PPT files to silence content-quality findings unless a deterministic compiler
bug is confirmed.

## Step 7: Pre-PPT Gate

```bash
"$PYTHON_CMD" scripts/validate_stage_gate.py \
  --stage pre_ppt \
  --run-dir . \

```
